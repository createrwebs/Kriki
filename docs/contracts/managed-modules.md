# Managed module control contract

Status: implementation in progress; business data/commerce readiness is not yet enabled.

Authenticated verified owner endpoints under `/lab/{project}/modules` use session+CSRF, strict JSON and private/no-store responses. Project context comes from route binding and ownership, never body owner/project fields.

- `GET /`: catalog, effective capability selection, project revision and installation metadata; readable when frozen or downgraded. No Supabase tokens or customer records.
- `PUT /capabilities/{key}`: `{enabled:boolean,expected_revision:integer>=0}`; corresponding account plan feature required, owner project writable. Unknown keys422, denied403/402, stale409. Every state change increments project module revision. No automatic plan grants.
- `POST /`: `{key,expected_revision,config:{},idempotency_key:UUID}`; prepares one installation per project/key with selected Supabase ref. Dependencies must already be ready/enabled. Exact key/hash retry returns200 existing installation; new201. Different request with same idempotency or existing key409. No schema write or activation.
- `PATCH /{installation}/state`: `{state:enabled|disabled,expected_revision:integer>=1}`; exact project installation binding. Enable requires verified schema ready and dependencies. Disable retains all records/history.

Installation fields: uuid,key,revision,schema_version,status(prepared|ready|failed),enabled. Business data remains in account-selected pinned Supabase, with module+project predicates. Ref changes require reconnecting the original project; no automatic rebind.

New account feature codes `lab_module_{key}` are default-denied and appear in the existing entitlement catalog for explicit operator plan configuration. Existing booking authorization is retained through its original API; enabling commerce is never a side effect of booking adoption.

New business writes additionally require server readiness gate after S1–S4 evidence. Hiding a button is not authorization. External schema Apply will be a separate concrete server-issued proposal; client booleans cannot approve SQL.

Schema approval endpoints under the same owner prefix:

- `POST /{installation}/proposals` accepts only `{expected_revision:integer>=1}`. The server issues a fixed `install_module` proposal, valid for 15 minutes, bound to actor/project/installation/pinned ref/module revision/SQL hash. Contact, news, catalog, orders and manual payments v1 have code-owned schemas. No caller SQL or acknowledgement field is accepted.
- `GET /proposals/{proposal}` returns the exact code-owned DDL, impact hash, expiry and receipt to its owner. It makes no remote change.
- `POST /proposals/{proposal}/apply` accepts only `{impact_hash:64 lowercase hex,expected_revision:integer>=1}`. Authenticated owner CSRF confirmation is required; rechecks capability, dependency, pinned ref, immutable payload, expiry and revision under locks. One schema apply lease per project. An applied proposal returns its receipt without re-execution. Storage failures redact upstream bodies and never mark the installation ready. Remote DDL is transactional and idempotent for safe retry after a lost response.
- `POST /proposals/{proposal}/cancel` accepts `{}`; preserves a cancelled receipt and never calls Supabase.

Installation uses Supabase Management `POST /v1/projects/{ref}/database/query` with the server OAuth token and `read_only:false`, then verifies/registers the exact project/module through a service-role-only RPC. The query endpoint is experimental in the [Supabase contract](https://supabase.com/docs/reference/api/v1-run-a-query); only a verified schema marker plus the exact registration response permits ready state. No credentials are returned to the editor or generated artifact.

Independent quote rate10/minute/IP/module and100/minute/module.

Changed/consumed quote409 requires an explicitly reviewed fresh quote; no automatic creation at a changed amount. Caller prices, totals, recipient and status are rejected. One quote is consumed by one creation key atomically. Matching accepted creation-key/hash retries return exact saved snapshots after quote expiry or module disable while guest access remains valid. - Creation returns a64-hex HMAC-derived capability; only its SHA-256 hash is stored. Reads/uploads use `X-Krikkit-Order-Token`, never URL query parameters or platform credentials. Valid for24 hours from server creation; owner `POST /{installation}/orders/{order}/revoke-access` with `{}` records actor/time/event idempotently and guest operations return404 thereafter. Revocation and authorized owner history remain available after downgrade, disable or freeze on the original pinned datastore.
- Public order creation limit is16KiB JSON. Slip transport remains JSON data URLs, maximum7100000 JSON bytes and5MiB decoded bytes, PNG/JPEG/WebP only. Server inspects actual MIME/dimensions, decodes at most20MP and re-encodes PNG without metadata; missing decoder503. Disguised HTML, SVG or mismatched types422. New PNG bytes are uploaded without upsert to a per-module verified private Storage bucket; attempts retain only metadata. The reviewed schema creates a restrictive Storage policy which preserves unrelated buckets and blocks anonymous/authenticated access even under unrelated broad permissive policies.
- Staged upload receipts carry immutable random object paths, content hash and lease ownership. PostgreSQL commit atomically records attempt, pending-review order and receipt. Cleanup must first claim an uncommitted receipt under a row lock; ambiguous successful commit never deletes evidence. `POST /{installation}/slip-uploads/reconcile` with `{}` checks at most10 expired receipts; immutable abandoned tombstones permit later cleanup of delayed workers without touching replacement uploads. No cross-service atomicity or automatic evidence retention deletion is claimed.
- Upload limits:5/minute/order,20/hour/order,100/hour/module. A slip creates `submitted` / order `pending_review`; it never confirms payment. Normalized payer/reference/claimed-time/amount/image hash are part of idempotency. Server upload time is distinct from the unverified claimed transfer time.
- Review requires authenticated owner, effective manual-payments policy, expected-version CAS and a reason for rejection. Acceptance additionally requires `bank_verified:true` and matching order amount. Actor is derived from the session. PostgreSQL locks the order and attempt; paid/cancelled orders reject later reviews. Accept/reject events preserve actual previous state. The owner must check the bank independently; this acknowledgement does not verify money through a bank API.
- Generated storefront keeps only module-scoped product UUID/quantity in localStorage and order UUID/capability/expiry in sessionStorage. Customer details and slips are not persisted in browser storage. Storage denial is handled without crashing. Pending review hides duplicate slip submission; rejection allows a new attempt with a new idempotency key even for the same file.

## Build/import admission leases

`POST /lab/{project}/operations` accepts strict small JSON `{operation:'build',operation_key:UUID}` using verified owner session+CSRF. Project must be writable and executable according to RuntimePolicy; PHP source-only projects423. Two active build/import leases per account are allowed; schema Apply has one separate lease per project. Duplicate exclusive start409, exhausted concurrency429.

`PATCH /lab/{project}/operations/{operation}` accepts `{state:active|completed|failed}`. Active renewal rechecks ownership, writable project, active lease UUID and five-minute expiry. Finalization is allowed for an owner after freeze so work can release its slot. A stale lease cannot finalize a replacement. Responses are private/no-store. These routes do not execute customer source on the host.

Actual browser build acquires before runtime preparation, renews every minute, passes a linked abort signal into package preparation/process spawn/output waiting, and finalizes in cleanup. Renewal failure cancels running work and prevents packaging/promotion. GitHub import and artifact deployment acquire inside their real handlers before destructive workspace preparation/deployment. Lost client cleanup releases by five-minute lease expiry. Admission accounting is not an OS resource sandbox or an attestation of arbitrary customer JavaScript.

## Generated commerce routes and build compatibility

A store at `/shop` exposes `/shop/cart`, `/shop/checkout`, `/shop/orders/{uuid}`; root placement uses `/cart`, `/checkout`, `/orders/{uuid}`. Normal pages preserve SiteContent, deep commerce routes avoid its unrelated404. Capabilities stay in session storage, never in URLs. A copied order URL without its matching session capability displays recovery guidance and cannot show another order.

Owner `GET /lab/{project}/modules/build-context` returns `context:null` for plain sites; managed sites require authenticated SDK3 ownership/config, canonical managed runtime files, current ready schemas and the original pinned datastore. The guest builder hashes every source file before/after build and packages `.krikkit-artifact.json` with source/schema/SDK/runtime versions and actual artifact byte hashes. Server rechecks under the workspace lock before stage/swap promotion. Failed/stale/incompatible builds preserve last-good files/live state and immutable payment history. Publication start/verify/unpublish/deploy share that lock; a late artifact cannot republish after unpublish. These checks are compatibility/integrity checks, not arbitrary customer JavaScript attestation. Host builds remain limited to code-owned fixtures.
